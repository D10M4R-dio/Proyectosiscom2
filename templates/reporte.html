1. Resumen Ejecutivo y Descripción del Sistema

El presente proyecto implementa un sistema de telemetría y monitoreo remoto en tiempo real a través de una plataforma Web alojada en un Servidor Virtual Privado (VPS) en la nube con dirección IP pública. El sistema captura variables físicas ambientales —Temperatura (°C) y Humedad Relativa (%)— junto con parámetros de radiocomunicación —Potencia de señal recibida RSSI (dBm)— mediante un nodo sensor basado en el microcontrolador ESP32 / ESP8266 y el transductor digital DHT22 (o DHT11).

Además de las variables primarias, el servidor calcula en tiempo real variables termodinámicas derivadas de alto valor en ingeniería: el Índice de Calor (Sensación Térmica en °C) mediante el modelo de regresión de Rothfusz (NOAA) y el Punto de Rocío (°C) mediante la ecuación de Magnus-Tetens, almacenando cada trama en una base de datos relacional SQLite y difundiendo las lecturas instantáneamente hacia los navegadores conectados mediante el protocolo Server-Sent Events (SSE).

2. Arquitectura de Comunicaciones y Pila de Protocolos

El sistema sigue una arquitectura de comunicaciones de tres capas extremo a extremo:

Capa del Sistema Tecnología / Protocolo Función en el Sistema de Comunicación
1. Nodo Sensor (Periferia IoT) ESP32 / ESP8266 + Sensor DHT22 + Simulador Python Adquisición digital de Temperatura y Humedad (protocolo 1-Wire) y empaquetamiento de telemetría en formato ligero JSON.
2. Red de Acceso y Transporte IEEE 802.11 (Wi-Fi) → IPv4 → TCP (Puerto 80) → HTTP/1.1 REST Transmisión confiable orientada a conexión desde la red local del sensor hacia la dirección IP pública del servidor en la nube mediante peticiones POST /api/readings.
3. Servidor Cloud (VPS IP Pública) Ubuntu Server + Nginx (Reverse Proxy) + Gunicorn + Flask + SQLite + SSE Recepción de tramas, validación, cálculo de variables derivadas, evaluación de umbrales de alerta, persistencia SQL y visualización Web interactiva en tiempo real.

3. Paso 1: Despliegue del Servidor Virtual en la Nube (VPS)

Para cumplir con el Requerimiento 1 y el Requerimiento 4 (ejecución sobre dirección IP pública), se aprovisionó una máquina virtual en la nube (compatible con DigitalOcean Droplet, Google Cloud Compute Engine, AWS EC2 o Microsoft Azure VM) con las siguientes especificaciones:

  • Sistema Operativo: Ubuntu Server 22.04 LTS / 24.04 LTS (64-bit).
  • Recursos: 1 vCPU, 1 GB RAM, 25 GB SSD.
  • Red e IP Pública: Interfaz de red con IPv4 Pública estática/efímera y regla de Firewall habilitando tráfico entrante en el puerto TCP 80 (HTTP) y TCP 22 (SSH).
# Conexión remota al servidor virtual mediante SSH usando su IP pública:
ssh root@<IP_PUBLICA_DEL_SERVIDOR>

4. Paso 2: Instalación y Configuración del Software para Servicio Web

Dentro del servidor virtual en la nube se ejecutaron los siguientes pasos para instalar el entorno de producción compuesto por Python 3, Gunicorn (Servidor WSGI de producción), Nginx (Servidor Web y Proxy Inverso) y Systemd (Demonio de ejecución continua 24/7): 

# 1. Actualizar índices de paquetes e instalar dependencias del sistema
sudo apt update && sudo apt upgrade -y
sudo apt install -y python3 python3-venv python3-pip nginx git ufw

# 2. Clonar o copiar los archivos del proyecto en /opt/proyectosiscom2
sudo mkdir -p /opt/proyectosiscom2
cd /opt/proyectosiscom2

# 3. Crear entorno virtual aislado e instalar Flask y Gunicorn
python3 -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt

# 4. Ejecutar el script automatizado de configuración de Nginx y Systemd
sudo bash deploy/setup_vps.sh

El servicio queda registrado en /etc/systemd/system/siscom-monitor.service ejecutando Gunicorn con workers gevent/gthreads, mientras que Nginx escucha directamente en el puerto 80 de la dirección IP pública y redirige el tráfico al backend local con soporte nativo para Server-Sent Events (SSE) (proxy_buffering off;).

5. Paso 3: Formato de Trama de Comunicación y API REST

El dispositivo sensor envía periódicamente una petición HTTP POST al endpoint http://<IP_PUBLICA>/api/readings con cabecera Content-Type: application/json y la siguiente estructura de carga útil (payload): 

POST /api/readings HTTP/1.1
Host: <IP_PUBLICA_SERVIDOR>
Content-Type: application/json

{
  "device_id": "ESP32-NODO-01",
  "location": "Laboratorio Comunicaciones II",
  "temperature": 25.8,
  "humidity": 59.2,
  "rssi": -56,
  "battery_v": 3.32
}

6. Paso 4: Programación del Nodo Sensor (ESP32 / Simulador)

El proyecto incluye dos mecanismos complementarios de transmisión de datos hacia la IP pública:

  1. Firmware para Microcontrolador (firmware/esp32_dht_monitor/esp32_dht_monitor.ino): Conecta el módulo ESP32/ESP8266 a la red Wi-Fi, interroga el sensor DHT22 en el pin GPIO 4, mide el nivel de potencia recibida (WiFi.RSSI()) y transmite la trama JSON cada 5 segundos al servidor en la nube.
  2. Simulador de Telemetría en Python (simulator/sensor_simulator.py): Permite realizar pruebas de carga, simular variaciones sinusoidales realistas o inyectar eventos térmicos críticos hacia la IP pública para verificar las alarmas del Dashboard en tiempo real.

7. Pruebas de Funcionamiento y Conclusiones

  • Baja Latencia de Actualización: Gracias al uso de Server-Sent Events (SSE) sobre HTTP persistente, cada lectura enviada por el sensor aparece graficada en el navegador web en menos de 100 ms sin necesidad de recargar la página.
  • Persistencia y Exportación: Todas las lecturas quedan almacenadas en SQLite y pueden descargarse en formato CSV desde el botón Exportar CSV para procesamiento estadístico.
  • Disponibilidad sobre IP Pública: La combinación de Nginx como proxy inverso y Systemd garantiza que el servicio web permanezca accesible desde cualquier red externa a través de la dirección IP pública del servidor virtual.
